### Замечание 1 — удаление в обычном режиме (важно)

В карточке приложения One UI 8 показывает кнопку **«Deactivate and uninstall»**: администратор снимается
и приложение удаляется одним нажатием, предупреждение `onDisableRequested` не показывается.

- Это ограничение обычного режима Android, а не ошибка кода. Закрыть его могут только служба доступности
  (перехват экрана настроек, спринт 3) или Device Owner.
- **Тексты приложения обещали «нельзя удалить»** — исправлено в `fix/honest-admin-texts` на всех 4 языках.
- Критерий спринта 1 «удаление требует пароль» в обычном режиме **не выполнен**; в режиме Device Owner —
  ещё не проверен.

### Замечание 2 — `adb reverse` сбрасывается

Правило проброса порта пропадало несколько раз за сеанс (переподключение USB на Samsung). На время
проверки помогает фоновый цикл, повторяющий `adb reverse tcp:8080 tcp:8080` каждые 3 секунды.

### Не проверено

- Device Owner: запрет удаления, безопасного режима, сброса — нужен отдельный тестовый телефон.
- Xiaomi/Tecno/Infinix: шаг «Работа в фоне» и выживание службы.
- Узбекский и русский интерфейс на телефоне (язык системы был английский).
- Release-сборка с `https://api.maxcare.dexx.uz` и привязкой сертификата — сервер ещё не развёрнут.

### Замечание 1 — первая отметка «на связи» только через 15 минут
Администратор был активен с прошлого сеанса, поэтому служба запустилась при открытии приложения,
до привязки. Первая отправка прошла без токена, следующая — через 15 минут. Исправление: отправлять
сразу после успешной привязки.

### Замечание 2 — ложное `notifications_off` во время настройки
Служба увидела выключенные уведомления до шага «Разрешить уведомления» и записала событие.
Исправление: записывать только переход «были включены → выключены».

### Замечание 3 — событие без сети после снятия защиты (логика, найдено при разборе п. 5)
После отключения администратора служба останавливается, и периодической отправки больше нет. Если в этот
момент нет сети, `admin_disabled` ждёт в очереди до следующего открытия приложения или включения телефона.
Исправление: при неудачной отправке ставить задачу WorkManager с условием «есть сеть».

### Замечание 1 — адресную строку Chrome прочитать нельзя (ожидаемо)

Chrome по omnibox шлёт `TYPE_VIEW_TEXT_CHANGED` с **пустым источником и пустым `event.text`** — браузер
намеренно не отдаёт содержимое адресной строки службам доступности. Прочитать этот текст через
accessibility невозможно.

- Это ограничение браузера, не ошибка кода. Адресная строка закрыта **DNS-фильтром (спринт 2)**:
  SafeSearch и блок-листы срабатывают при переходе по адресу/запросу. Текстовый фильтр по доступности —
  дополнение (внутристраничные поля поиска, выдача).
- Наблюдение для PR 2: Vivaldi кладёт запрос в `TYPE_WINDOW_STATE_CHANGED`/`WINDOW_CONTENT_CHANGED`
  (не в редактируемое поле). Фильтрацию текста выдачи и чтение `event.text` как запасного источника
  забирает PR 2.

### Не проверено
- Включение службы через экран приложения с заметным раскрытием (Google Play) — UI ещё не сделан.
- Доставка `search_blocked` родителю (не было привязки/сервера в этом сеансе).
- Скорость очистки «< 1 c» строго не замерялась (визуально мгновенно).

## 13.10.2026 — Samsung S24 Ultra, спринт 4: периодический таймер + надёжность захвата

Событийный захват (на событиях браузера) пропускал контент — Chrome шлёт события
нерегулярно. Заменили на **периодический таймер**: кадр раз в ~1.5 с, пока на переднем
плане браузер/мессенджер (`ScreenshotScanner.startLoop`, трекинг пакета в службе).
Диагностика сырого скора — временным логом (убран).

**Главная находка (диагностикой, порог 0.75):**
- Модель **правильно** оценивает откровенные кадры: за сессию десятки кадров 0.60–0.99,
  сработали блокировки (`image_blocked_nudity`).
- Но `takeScreenshot` на веб-поверхности Chrome **периодически возвращает пустой/чёрный
  кадр** (скор ~1e-5), чередуя с настоящим контентом (0.9+). Отсюда «то ловит, то нет».

**Вывод:** детекция и модель работают; нестабильность — в **надёжности самого скриншота**
веб-контента, не в коде фильтра. Это ключевая задача тюнинга для PR 5.

### Идеи для PR 5 (надёжность захвата)
- Отбрасывать «почти чёрные»/пустые кадры (не считать их SAFE, а пропускать как невалидные).
- Брать максимум скоров за короткое окно, а не по одному кадру.
- Повтор захвата при подозрительно нулевом кадре.
- Проверить, не теряется ли веб-контент в скриншоте из-за аппаратной композиции (возможно,
  нужен другой момент/способ захвата).
- Плюс: порог (0.75 даёт ~7.4% пропусков — рассмотреть 0.5), размытие, замер батареи при
  непрерывном захвате раз в 1.5 с.
