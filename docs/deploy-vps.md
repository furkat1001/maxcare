# Сервер MaxCare на VPS — настройка

Решение от 2026-10-23: **Hostinger VPS KVM 2** (2 vCPU, 8 ГБ RAM, 100 ГБ NVMe), Ubuntu 24.04 LTS
без панели управления, дата-центр в **Германии или Франции**.

Почему так:
- нужен VPS, а не веб-хостинг: сервер — Kotlin/Ktor (JVM) + PostgreSQL + Redis в Docker;
- Hetzner Cloud после повышения цен 15.06.2026 дороже, а дешёвые линейки (CX, CAX) «нет в наличии»;
- страна: с 26.03.2026 закон Узбекистана о персональных данных требует хранить в стране только
  биометрию, генетические и абонентские данные; Германия и Франция — в списке 49 стран для
  упрощённой передачи (август 2026). Литвы в опубликованном списке нет. **Подтвердить у юриста**
  вместе с регистрацией базы ПД (roadmap, «Неделя 0»); до ответа не оплачивать надолго вперёд.

Секреты (пароль root, пароль `deploy`, закрытый SSH-ключ, `MAXCARE_SECRET_KEY`, пароль базы)
в репозиторий и в чат не попадают.

## 0. SSH-ключ на компьютере (Windows, PowerShell)

```
ssh-keygen -t ed25519 -C "maxcare-server"
```

- путь — Enter (по умолчанию `C:\Users\<имя>\.ssh\id_ed25519`);
- passphrase — задать (защита ключа, если файл утечёт).

Открытый ключ для Hostinger: `Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub` — строка
`ssh-ed25519 … maxcare-server` целиком; имя ключа в Hostinger — по компьютеру (`probook-laptop`).
Файл без `.pub` — закрытый ключ, никуда не отправлять.

При покупке: «What to install» → Operating system → **Ubuntu 24.04 LTS** (или шаблон «Docker»
на Ubuntu 24.04). Панели (cPanel, CyberPanel, CloudPanel…) и приложения — не нужны. Docker
Manager можно включить для просмотра, но контейнеры MaxCare управляются только через
`docker compose` из репозитория.

## 1. Первый вход и пользователь `deploy`

IP-адрес — в hPanel. На компьютере:

```
ssh root@IP
```

На сервере, по одной команде:

```
apt update && apt -y full-upgrade
adduser deploy
usermod -aG sudo deploy
mkdir -p /home/deploy/.ssh && cp /root/.ssh/authorized_keys /home/deploy/.ssh/
chown -R deploy:deploy /home/deploy/.ssh && chmod 700 /home/deploy/.ssh && chmod 600 /home/deploy/.ssh/authorized_keys
```

**Не закрывая окно root**, во втором окне проверить:

```
ssh deploy@IP
sudo whoami      # → root
```

Только после успешной проверки — шаг 2: иначе можно потерять доступ к серверу.

## 2. Защита SSH, файрвол, автообновления

Под `deploy`:

```
printf 'PermitRootLogin no\nPasswordAuthentication no\nKbdInteractiveAuthentication no\n' | sudo tee /etc/ssh/sshd_config.d/00-hardening.conf
sudo sshd -t && sudo systemctl restart ssh
```

Файл с префиксом `00-` читается первым и перекрывает `50-cloud-init.conf`, который на Ubuntu
может разрешать вход по паролю. Проверить в **новом** окне, что `ssh deploy@IP` по-прежнему
пускает, а `ssh root@IP` — нет.

```
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo apt -y install unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades
```

Docker публикует порты в обход `ufw`, поэтому в `docker compose` наружу открываются только 80 и
443 (Caddy); PostgreSQL и Redis — только во внутренней сети Docker.

Docker (если не ставился шаблоном или Docker Manager):

```
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker deploy    # перезайти по SSH
```

## 3. Домен и TLS

- DNS-запись `A`: `api.maxcare.dexx.uz` → IP сервера (у регистратора / DNS-провайдера `dexx.uz`).
- Сертификат — **только Let's Encrypt**: приложение ребёнка закрепляет корни Let's Encrypt
  (`android/app-kids/src/main/res/xml/network_security_config.xml`, срок привязки до 2027-10-01).
  В Caddy указать ACME-издателя Let's Encrypt явно, без запасного ZeroSSL.

## 4. Что ещё сделать (в репозитории, не начато)

- `Dockerfile` сервера и `docker-compose` для продакшена: сервер, PostgreSQL, Redis, Caddy (TLS).
- Шаблон переменных окружения (`MAXCARE_SECRET_KEY`, `MAXCARE_DB_*`, `MAXCARE_REDIS_URL`,
  `MAXCARE_GOOGLE_CLIENT_IDS`); сами значения — только в файле на сервере.

## 5. Копии базы вне сервера

`deploy/backup.sh` каждую ночь делает копию на сервере, шифрует её и отправляет в Backblaze B2.
Копия содержит данные детей, поэтому наружу уходит **только зашифрованный файл** (age, лицензия
BSD-3; отправка — rclone, лицензия MIT). Хранилище видит лишь шифротекст.

**Два разных ключа, и оба не позволяют навредить, если сервер взломают:**

- Шифрование: на сервере только **открытый** ключ age. Прочитать копии он не позволяет. Закрытый
  ключ — только у владельца, в менеджере паролей. **Потеря закрытого ключа = потеря всех копий.**
- Хранилище: ключ B2 с типом Write Only, только на один бакет. Читать копии он не может, а вот
  право `deleteFiles` у этого типа ключа **есть** (проверено: Backblaze выдаёт его и Write Only).
  От удаления защищает Object Lock: 30 дней неизменяемости у каждой копии.

Срок хранения: 30 дней неизменяемости (Object Lock), затем правило бакета скрывает файл и через
день удаляет. Веб-интерфейс Backblaze спрашивает только число дней и, судя по его документации,
ставит режим Compliance: копию не может удалить раньше срока **никто, включая владельца**, кроме как
закрытием всего аккаунта B2. Поэтому срок короткий: данные семьи, удалённые из базы, остаются в
зашифрованных копиях не дольше 31 дня. Об этом нужно сказать в политике конфиденциальности. Object
Lock на бакете выключить нельзя; срок по умолчанию менять можно, но только для новых файлов.

**Для восстановления нужен ещё `.env` с прежним `MAXCARE_SECRET_KEY`**: им зашифрованы секреты
привязанных телефонов. Его копия тоже должна лежать в менеджере паролей.

### Настройка

1. Backblaze: регион US East (страна из перечня постановления КМ РУз № 415), приватный бакет,
   правило Lifecycle (`daysFromUploadingToHiding: 30`, `daysFromHidingToDeleting: 1`), Object Lock
   со сроком 30 дней, ключ Application Key: только этот бакет, Write Only.
2. На сервере: `sudo apt -y install age rclone`.
3. Создать `deploy/.env.backup` по образцу `deploy/env.backup.example`, права 600.
4. Проверить: `cd /opt/maxcare/deploy && ./backup.sh`. В журнале должно появиться `offsite ok`.

### Восстановление и его проверка

1. Скачать нужный файл `*.sql.gz.age` из веб-интерфейса Backblaze и положить на сервер.
2. Закрытый ключ age сохранить во временный файл с правами 600.
3. Проверка без риска для рабочей базы: `./restore-check.sh <файл.age> <файл с ключом>`. Скрипт
   разворачивает копию во временной базе и печатает только количества строк.
4. Настоящее восстановление: в **пустую** базу загрузить результат
   `age -d -i <ключ> <файл.age> | gunzip`, затем запустить сервер с прежним `.env`.
5. Удалить файл с ключом: `shred -u <файл с ключом>`.

Проверять восстановление раз в квартал: копия, которую ни разу не разворачивали, — ещё не копия.
Сбой отправки виден в `/var/log/maxcare-backup.log` как `OFFSITE FAILED`.

## 6. Оповещения

Сообщения приходят в Telegram от своего бота, только при смене состояния («сломалось» и «починилось»),
а пока проблема не решена, раз в 6 часов приходит напоминание. Наружу уходят только технические
причины, никаких личных данных. Сторонних сервисов, кроме Telegram и GitHub, нет.

| Что проверяет | Как часто | О чём сообщает |
| --- | --- | --- |
| `deploy/health-check.sh` на сервере | каждые 5 минут | упал контейнер, не открывается `/health`, диск занят на 85 %+, памяти меньше 150 МБ, сертификат истекает через 14 дней и меньше, нет копии свежее 26 часов |
| `deploy/backup.sh` на сервере | ночью | копия не сделана, дамп неполный или не отправилась копия вне сервера |
| `.github/workflows/uptime.yml` на GitHub | примерно каждые 30 минут, запуск может задерживаться | сервер не отвечает снаружи, в том числе если он пропал совсем |

Перед тревогой о сбое `health-check.sh` повторяет проверку через минуту, а проверка снаружи делает три
попытки: короткий перезапуск не будит ночью. `backup.sh` проверяет, что дамп дописан до конца, и не
сохраняет обрезанный.

**Что важно знать:**

- Проверка снаружи идёт из-за границы. При сбое международного канала придёт тревога, хотя внутри
  Узбекистана сервис может работать. Об этом сказано в самом сообщении.
- Репозиторий приватный: бесплатно 2000 минут Actions в месяц, проверка снаружи берёт около 1440, на
  сборки Android и backend остаётся около 560. Когда минуты кончаются, проверка снаружи молча
  останавливается до начала следующего месяца. Расход виден в Settings → Billing and plans → Usage.

### Настройка

1. Создать бота у `@BotFather`, написать ему любое сообщение, узнать числовой ID своего чата.
2. На сервере создать `deploy/.env.monitor` по образцу `deploy/env.monitor.example`, права 600.
3. В GitHub: Settings → Secrets and variables → Actions, секреты `MAXCARE_TELEGRAM_BOT_TOKEN` и
   `MAXCARE_TELEGRAM_CHAT_ID`.
4. Расписание у пользователя `deploy` (`crontab -e`) и файл журнала `/var/log/maxcare-health.log` с
   владельцем `deploy`:

```
0 3 * * * cd /opt/maxcare/deploy && ./backup.sh >> /var/log/maxcare-backup.log 2>&1
*/5 * * * * cd /opt/maxcare/deploy && ./health-check.sh >> /var/log/maxcare-health.log 2>&1
```

### Проверка

- На сервере: в спокойное время `docker compose stop redis`, дождаться сообщения, `docker compose start
  redis`, дождаться сообщения о восстановлении.
- На GitHub: Actions → uptime → Run workflow, указать заведомо неверный адрес. Должна прийти тревога,
  а после следующего обычного запуска — сообщение о восстановлении.
